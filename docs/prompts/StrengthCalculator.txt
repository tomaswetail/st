Implement a team-strength feature system for the football prediction engine.

The goal is to improve 1/X/2 probabilities by measuring **underlying attacking and defensive performance**, rather than relying mainly on recent results.

The implementation must use the project's existing:

* `Match`
* `Team`
* `League`
* historical FotMob/SofaScore match data
* xG / shot data tables
* database/session architecture
* prediction pipeline
* repository/service patterns
* configuration patterns

Inspect the existing codebase first. Do not duplicate models or introduce a parallel prediction architecture.

# Objective

For every upcoming match, calculate historical pre-match features describing:

```text
non_penalty_xg_for
non_penalty_xg_against

shot_quality_for
shot_quality_conceded

home_attack_strength
home_defence_strength

away_attack_strength
away_defence_strength

opponent_adjusted_attack_strength
opponent_adjusted_defence_strength

recency_weighted_attack_rating
recency_weighted_defence_rating

set_piece_xg_for
set_piece_xg_against

goalkeeper_goals_prevented
goalkeeper_prevention_rating
```

Also implement a Dixon-Coles goal model capable of producing:

```text
expected_home_goals
expected_away_goals

p_home
p_draw
p_away
```

These features must be calculated using **only information available before the target match**.

No future-data leakage is allowed.

# 2. Non-penalty xG

Calculate separately:

```text
npxg_for
npxg_against
```

For each historical match:

```python
npxg_for = sum(
    shot.xg
    for shot in team_shots
    if not shot.is_penalty
)

npxg_against = sum(
    shot.xg
    for shot in opponent_shots
    if not shot.is_penalty
)
```

If reliable match-level non-penalty xG already exists, reuse it.

Do not estimate missing xG as zero.

Missing data must remain `None` or be excluded according to a clearly documented rule.

Calculate:

```text
npxg_for_per_match
npxg_against_per_match
npxg_difference
```

# 3. Shot quality

Measure shot quality separately from shot volume.

Calculate:

```python
average_shot_xg_for = total_xg_for / shots_for

average_shot_xg_against = total_xg_against / shots_against
```

The defensive metric:

```text
shot_quality_conceded
```

should therefore represent the average xG value of shots allowed.

Also expose:

```text
shots_for_per_match
shots_against_per_match

shots_on_target_for_per_match
shots_on_target_against_per_match
```

This helps distinguish:

```text
Team A:
15 shots
0.8 xG

Team B:
8 shots
1.6 xG
```

Team B is generating much better chances despite taking fewer shots.

# 4. Recency weighting

Recent matches should matter more than older matches.

Implement configurable exponential weighting:

```python
weight = decay ** matches_ago
```

Default:

```text
decay = 0.90
```

Example:

```text
most recent match: 1.00
1 match ago:       0.90
2 matches ago:     0.81
3 matches ago:     0.729
...
```

Implement a reusable weighted mean:

```python
weighted_mean(values, weights)
```

Use recency weighting for:

```text
npxg_for
npxg_against

xg_for
xg_against

shot_quality_for
shot_quality_conceded

set_piece_xg_for
set_piece_xg_against
```

Expose:

```text
recency_weighted_attack_rating
recency_weighted_defence_rating
```

Do not weight based simply on calendar days unless the existing architecture already does so.

---

# 5. Separate home and away strength

Do not calculate only one generic team-strength rating.

Calculate:

```text
home_attack_strength
home_defence_strength

away_attack_strength
away_defence_strength
```

For example:

```python
home_attack_strength =
    team's weighted home npxG_for
    / league weighted home npxG average

home_defence_strength =
    team's weighted home npxG_against
    / league weighted away npxG average
```

Equivalent calculations should exist for away performance.

Interpretation:

```text
attack > 1.0 = above-average attack

attack < 1.0 = below-average attack

defence < 1.0 = better-than-average defence

defence > 1.0 = worse-than-average defence
```

Document the semantics clearly.

Apply minimum-sample safeguards.

If home/away samples are too small, shrink toward the team's overall rating.

---

# 6. Regression / shrinkage

Small samples must not produce extreme ratings.

Implement configurable Bayesian-style shrinkage:

```python
shrunk_rating = (
    sample_size * observed_rating
    + prior_strength * prior_rating
) / (
    sample_size + prior_strength
)
```

Default prior:

```text
prior_rating = 1.0
```

Example configurable value:

```text
prior_strength = 8 matches
```

Apply shrinkage to:

```text
home attack
home defence
away attack
away defence
goalkeeper ratings
set-piece ratings
```

Do not allow a newly promoted team with two matches to receive extreme ratings solely from those two observations.

---

# 7. Opponent-adjusted performance

Raw xG can be misleading because fixture difficulty differs.

Example:

```text
1.4 xG against Manchester City

may represent a much better attacking performance than:

1.8 xG against the weakest defence in the league
```

Create opponent-adjusted ratings.

At minimum, calculate an adjustment based on the opponent's historical defensive/attacking strength before that historical match.

Example concept:

```python
adjusted_attacking_performance =
    observed_npxg_for / opponent_expected_npxg_conceded
```

and:

```python
adjusted_defensive_performance =
    observed_npxg_against / opponent_expected_npxg_created
```

Then calculate recency-weighted averages.

Avoid circular calculations where possible.

A preferred implementation is an iterative rating approach:

```text
1. Initialize all teams at league average.

2. Calculate attack/defence performance.

3. Adjust each historical match for opponent quality.

4. Recalculate ratings.

5. Repeat until ratings stabilize or max iterations are reached.
```

Expose:

```text
opponent_adjusted_attack_strength
opponent_adjusted_defence_strength
```

Make:

```text
max_iterations
convergence_tolerance
```

configurable.

Do not use the opponent's future rating.

# 9. Goalkeeper prevention

When xGOT / post-shot xG is available, calculate goalkeeper performance.

At the match level:

```python
goals_prevented =
    xgot_faced - goals_conceded
```

Positive:

```text
keeper prevented more goals than expected
```

Negative:

```text
keeper conceded more goals than expected
```

Calculate:

```text
goalkeeper_xgot_faced
goalkeeper_goals_conceded
goalkeeper_goals_prevented
goalkeeper_goals_prevented_per_90
```

Do not rely heavily on raw goalkeeper prevention over small samples.

Apply aggressive regression toward league average.

Example:

```python
regressed_keeper_rating = (
    shots_faced * observed_rating
    + prior_shots * league_average_rating
) / (
    shots_faced + prior_shots
)
```

Make `prior_shots` configurable.

If the expected goalkeeper for an upcoming match is known, use that goalkeeper.

Otherwise use a team-level weighted goalkeeper rating based on recent minutes.

Never treat missing xGOT as zero.

# 10. Performance versus results

The model must distinguish actual results from underlying performance.

Example:

```text
Team A last 3:

Won 1-0
xG: 0.6 - 1.8

Won 2-1
xG: 0.8 - 1.7

Won 1-0
xG: 0.5 - 1.4
```

This should NOT produce the same strength increase as:

```text
Team B last 3:

Won 2-0
xG: 2.1 - 0.7

Won 3-1
xG: 2.5 - 0.9

Won 2-0
xG: 1.9 - 0.5
```

Underlying xG performance should dominate short-term win/loss streaks in the team-strength model.

Do not create a feature equivalent to:

```text
last_5_wins
```

and allow it to dominate the ratings.

Results may exist as secondary features, but underlying performance must be kept separate.

# 12. Dixon-Coles model

Implement a separate Dixon-Coles goal model.

It should estimate:

```text
home_attack
home_defence
away_attack
away_defence
home_advantage
rho
```

Use historical scorelines to fit the model.

Expected goals should be calculated approximately as:

```python
lambda_home = (
    league_home_goal_rate
    * home_attack_strength
    * away_defence_strength
)

lambda_away = (
    league_away_goal_rate
    * away_attack_strength
    * home_defence_strength
)
```

Adapt the exact parameterization to a standard Dixon-Coles implementation.

Calculate Poisson score probabilities:

```text
0-0
1-0
0-1
1-1
2-0
0-2
2-1
1-2
...
```

up to a configurable maximum score, for example:

```text
max_goals = 10
```

Apply the Dixon-Coles low-score correction to:

```text
0-0
1-0
0-1
1-1
```

using parameter:

```text
rho
```

Then aggregate:

```python
p_home = sum(P(home_goals > away_goals))

p_draw = sum(P(home_goals == away_goals))

p_away = sum(P(home_goals < away_goals))
```

Ensure:

```python
p_home + p_draw + p_away == 1
```

within floating-point tolerance.

# Implementation requirements

Before changing code:

1. Inspect how existing `Match`, `Team`, `League`, xG and shot data are stored.
2. Inspect the existing prediction/ML feature pipeline.
3. Identify reusable repositories/services.
4. Show the proposed files/classes that need to be added or modified.
5. Explain how historical leakage will be prevented.

Then implement the feature system.

Keep these concerns separated:

```text
raw data ingestion
        ↓
historical statistics
        ↓
team-strength calculations
        ↓
Dixon-Coles
        ↓
ML feature generation
        ↓
probability model
```

Do not mix HTTP/FotMob/SofaScore fetching into the strength calculation layer.

The strength layer should operate entirely on normalized data already stored in the database.

Prioritize correctness, historical reproducibility, no data leakage, and testability over clever abstractions.
